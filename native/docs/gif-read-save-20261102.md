# GIF 读取与另存工程闭环（2026-11-02）

需求：FS-002。迁移依据为 legacy `core/gif-import.ts`、同名测试、`document-files.ts` 和 `imported-palette.ts`。已有“GIF 导入当前时间轴”的业务命令保留，本批更正共同读取器。

## 问题与结果

原生读取器曾只从 WIC 字符串元数据寻找循环标记，遗漏实际应用扩展；把0时长变为1ms；在读取局部帧前裁小尺寸，可能造成源缓冲区与读取步长不匹配；拒绝完全落在画布外的帧；以文件基名作为工程身份，并把原始GIF当工程ZIP归档保留。这些行为影响动画播放、同名文件独立性和导入后另存工程。

现在直接承接旧版合成规则：透明画布起步、透明补丁不覆盖、每帧先保存可见结果再执行清理。disposal=2只清除裁切后的局部矩形；disposal=3恢复此帧绘制前的画布；越界按画布相交裁切，完全在画布外的补丁不改变像素。

循环采用 `parsedGifLoops` 的两个精确应用标识 NETSCAPE2.0／ANIMEXTS1.0，忽略大小写；与旧版一样，不将扩展内有限重复次数解释为有限播放。GIF中0时长或缺少控制块时为100ms（旧版gifuct-js到gif-import的实际组合行为），其余按1—60000ms归一化。

原生必要适配：用有边界检查的GIF块扫描读取尺寸、局部帧、控制块和应用扩展；LZW、交错扫描、局部颜色表与透明索引继续由现有WIC解码器负责。先完整读出补丁，再用旧版规则合成；不复制新的解压算法。

新工程名称沿用源文件名（含.gif），默认激活第一帧，色板沿用导入提取。每次解码产生独立GUID工程身份，不因文件同名而误激活另一目录的工程。保留来源图片路径、打开后的clean状态；GIF字节不再作为原生工程归档。另存工程走正常新工程编码，源GIF保持原样。

## 边界

保留当前原生每边1—1024像素和10000帧上限；读入文件及展开像素工作各使用256MiB预算，展开预算计入帧、合成／恢复缓冲区和最大补丁。块截断／非法几何／超预算在加入作品前失败。不把这些原生限制说成旧版动态资源策略完全相同。

普通 `openPath` 的同步调度没有在本批改动；未宣称旧版后台加载的性能等价，也不宣称WIC与浏览器解码器对所有损坏文件的容错一致。PNG等其他读取器保持原行为。

## 验收

- `gif-import-tests`：沿用旧版两组补丁期望；真实GIF经过WIC验证透明帧、背景清理、恢复前帧、边缘／完全越界、双循环标记及未知标记、大小写、无／零／过长时长、交错扫描、局部色表、中文文件名、同名独立身份、预算、截断和源字节不变。
- 原生工程编码／读取往返核对身份、循环、帧数、时长、像素与色板。
- 正式 `--timeline-gif-drop-check` 增加两个目录同名GIF各开一个标签，并实际另存MoonSprite工程，回归原有文件／序列／启动路由与原dirty工程保护。
- 结果：`gif-import-tests`、唯一正式Release构建和正式 `--timeline-gif-drop-check` 全部通过；550文件来源覆盖与差异格式检查通过。没有人工打开／拖放／截图验收。
