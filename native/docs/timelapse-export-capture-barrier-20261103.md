# 缩时导出等待正在生成的帧

## 旧版依据

`workspace-commands-history.ts::exportTimelapse`先await flushTimelapseCapture，再取得导出帧数并调用exportTimelapseFile。`workspace-recording.ts`等待已在进行的捕获任务，并通过现有失败任务队列重试；生成失败不得报告完整导出。相关证据为workspace-recording.test.ts和workspace-timelapse.test.ts。

这与prepareLocalTimelapseSave不同：已存在的内嵌PNG即使不能迁移到本机库，仍可读取；但尚未生成成功的新帧不能静默省略。此前移除导出入口的全量flush，解决了前者，却缺少后者的独立等待。本批补齐这一区别。

## 实现

Session增加捕获队列专用的显式重试／完成检查，直接调用既有CaptureQueue的retry、valid和commit，不触发嵌入快照的持久化游标或重试。导出表单提交时复用RecordingFlushDialog等待捕获任务，保持UI事件循环；完成后取当前快照列表和数量，再解析输出名、文件冲突并启动后台图片编码。

生成失败回到原表单，由既有状态行显示错误；不启动编码或输出，不清理待重试像素，也不改用户填写的名称、目录、格式和缩放。再次提交执行一次既有队列重试，无定时重试。正常保存／恢复使用原完整持久化等待。

原生适配边界：捕获PNG仍按现有架构先持久写入再发布到快照，因此新捕获落盘失败属于捕获未完成；现成内嵌录像迁移失败不属于捕获失败。本批不改变该存储架构。导出表单模态期间不接受新的用户绘画，未声称任意并发会话的队列时点完全等价。

## 验证

核心回归制造捕获队列写入失败，检查已有画作、历史和待处理任务保留；将本轮测试路径障碍改名保留后显式重试，核对捕获图像。另在内嵌录像持久化失败状态确认捕获等待直接完成、原PNG仍可导出。

正式--timeline-gif-drop-check在已打开的实际导出表单中产生第二笔，再提交导出；检查最终生成第二张PNG且其像素匹配当前画作。既有“库不可写但内嵌完整”的实际预览／导出与命名导出回归继续运行。

本批结果：唯一正式Release构建、timelapse-tests、正式程序--timeline-gif-drop-check、555文件来源覆盖及git diff --check通过。正式导出检查确认打开表单后新增的第二帧实际输出且像素匹配。未人工操作或截图验收；视频编码等已登记缺口不变。
