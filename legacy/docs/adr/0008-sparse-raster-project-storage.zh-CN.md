# ADR-0008：工程文件稀疏栅格存储

中文 | [English](0008-sparse-raster-project-storage.md)

## 状态

已接受

## 背景

大型 MoonSprite 工程可能包含数十个画布尺寸的图层与 Cel 表面，而有意义的像素只占每个表面很小一部分。ZIP Deflate 可以保持磁盘文件紧凑，但打开时编辑器仍要展开每个原始表面。因此，即使大部分瓦片透明，一个 `4596 x 1767` 的工程仍可能展开数百 MiB 数据。

## 决策

- 工程 schema v5 可以把每个图层或 Cel 存储为一个 `sparse-tiles-v1` 资源，其中只包含非零的 `64 x 64` 瓦片，不创建数千个 ZIP 条目。
- 写入器会按资源比较稀疏表示与原始表示的字节数，并保留较小者。RGBA 瓦片占用检查全部四个字节，从而无损保留 alpha 为 0 时隐藏的 RGB 值；索引格式把 ID 0 视为透明。
- 读取器验证完整瓦片目录，并重建一个覆盖已存储瓦片边界的连续栅格表面。它的画布偏移与稳定存储原点保留文档坐标，而工具、合成、历史、Store 和平台 API 继续使用现有连续表面契约。
- schema v1-v4 资源在内存中迁移为原始数据。首次保存会写入 schema v5，并可能选择稀疏存储。未知编码和格式错误的瓦片容器会被拒绝。
- 增量保存继续为每个栅格资源跟踪一份 CRC 与 revision。未改变的 v5 资源复用原路径、编码、尺寸、偏移和压缩 ZIP 条目；已改变的紧凑表面从当前运行时几何重新编码。
- 打开工程时，从解码后的清单、资源引用和 ZIP CRC 注册增量保存基线，不重新编码全部像素。Worker 路由根据清单估算展开后的栅格字节数，避免紧凑 v5 ZIP 把大额分配重新推回 UI 线程。

## 结果

大型稀疏工程从 ZIP 展开的字节显著减少，可以避免为每个资源已存储瓦片边界之外的透明空间分配内存，并且解码后无需再次完整扫描栅格。若内容分散在大多数图层边界框内的远距离瓦片中，运行时内存减少可能有限；此设计不是永久瓦片化的运行时。运行时渲染与编辑保留现有像素表示和视觉输出。密集资源可以继续使用原始表示，而保存后的 v5 文件需要支持 v5 的读取器，尽管 v5 读取器仍向后兼容 v1-v4。

## 替代方案

拒绝每个瓦片对应一个 ZIP 条目，因为数千个中央目录项会增加元数据、查询和合并开销。拒绝只保留原始资源，因为 Deflate 只减少磁盘体积，不减少展开解码工作。永久瓦片化运行时模型被推迟，因为它会跨越绘制、选区、撤销、合成和缓存所有权边界。
