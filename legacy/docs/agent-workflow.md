# AI 与开发工作流

中文
本文件是发布、性能和上下文恢复的唯一详细流程。日常硬规则见 [AGENTS.md](../AGENTS.md)，文档导航见 [README.md](README.md)。当前处于 Beta 迭代，实际版本号以项目清单的一致值为准；只有用户明确要求发布或打包时才进入发布阶段。

日常开发、风险分级和 `check:dev` 入口只以 [AGENTS.md](../AGENTS.md) 为准；本文件不重复这些规则。

## 任务调度

- 普通需求由一个 Agent 和一个写入者完成；不自动派生子 Agent，不在同一 checkout 并发写入。只读检索、测试和分析可以并行，写入并行必须使用独立 worktree。只有用户明确要求整项目架构审计或大型跨模块重构时，才启用一个只读架构 Agent。
- 普通任务使用 `gpt-5.6-terra` + `low`。`gpt-5.6-sol`/`ultra` 只用于用户明确要求或复杂架构任务；已有任务的模型覆盖不会因修改默认配置而改变，需新建或重启任务。
- 不用定时“继续”、后台轮询或无限重试。遇到 403/429 记录一次后等待服务恢复或换新轻量任务；磁盘不足和旧 rollout 只提示用户归档，不由 Agent 自动删除。
- 普通需求默认一个实现回合加一次定向检查，达到可验收状态就结束；默认上限为 20 次工具调用或 30 分钟。超出上限先汇报，复杂任务由用户明确放宽。

## 发布

用户明确要求“发布当前版本”“准备发布”或“生成安装包”后，按本周期基线审计完整差异：

```powershell
pnpm check:performance:release -- <本周期相关文件...>
pnpm check:performance:verify -- --audit=<审计编号> --correctness-passed
pnpm check:performance:accept -- --audit=<审计编号> --outcome=<adopted|not-adopted|approved-no-change> --reason=<原因>
pnpm check:release
```

性能审计每次只处理一个候选、最多两轮；像素、坐标、选区、撤销、格式、缓存和架构候选必须先获用户确认。没有超过噪声门槛的收益就接受为 `not-adopted`。`check:release` 先验证性能凭证，再运行静态维护契约、版本契约和 CHANGELOG 检查，以及边界契约测试、全量类型/测试、Web 构建和 Rust/缩略图检查；它不重复性能基准，也不生成安装包。

发布前集中更新中文 CHANGELOG、受影响契约、必要回归矩阵和架构状态；英文镜像只同步本周期实际改动的对应文件。安装包仅在用户明确要求时构建。

## 性能范围

- 普通需求不运行性能基准。性能专项、明显卡顿、关键依赖升级、大规模重构、里程碑或发布才运行审计。
- `pnpm check:performance -- <相关文件...>` 按文件选择套件；`pnpm check:performance:release -- <相关文件...>` 最低为 P3。
- 定向 P3 只运行与本次文件直接对应的轻量代表套件；完整标准、复杂、大画布和桌面矩阵只在发布审计或显式 `--all` 时运行。报告、分析、接受和凭证脚本走快速脚本测试，不触发 Canvas 基准。
- 性能审计不会猜测范围：省略文件会立即失败；只有显式 `--all` 才运行整个仓库的 P4 矩阵。命令固定为 `check:performance`（定向审计）、`check:performance:release`（发布审计）、`check:performance:verify`、`check:performance:accept` 和 `check:performance:receipt`。
- Canvas 候选以稳定样本比较已接受基线；每次只选一个候选。审计结果、基线和发布凭证由接受命令更新，普通检查不写入性能历史。

## 上下文恢复

压缩、换模型、暂停后继续只是同一需求的续接，不改变授权、风险或阶段：

- 优先使用摘要和已确认状态；缺事实时只定向读取一个文件或一个章节。
- 已成功检查的命令不因压缩重跑；先查看已有短报告。
- 每轮只做“新证据、一个根因假设、一个聚焦修改、最多一次直接检查”。连续两轮没有新 diff、结果或根因证据时停止并报告。
- 同一工作区只保留一个修改任务；需要并行时使用只读任务或独立工作树。
- 长日志、完整差异和大文件读取必须限定目标和输出范围。
